# 种子数据导入标准

> 约束范围：本项目自有导入流水线（爬取脚本、蒸馏脚本、`import_seeds.py`）。
> 外部 Agent 通过 API 写入的数据不受本标准强制约束，key 偏差不阻断写入，仅影响精确过滤命中率（语义检索不受影响）。

## 1. conditions 标准 key 对照表

`conditions` 为 JSONB 自由结构，本项目导入的数据**只允许使用以下 key**。新增 key 必须先在本表登记，再进入脚本：

| key | 类型 | 含义 | 示例 |
|---|---|---|---|
| `technologies` | string[] | 涉及技术/框架/语言 | `["rust", "axum"]` |
| `versions` | string[] | 关键版本号，含技术名前缀 | `["axum 0.8", "postgres 17"]` |
| `os` | string | 操作系统/运行环境 | `"macOS 26"` |
| `env` | string | 部署环境特征（云/容器/裸机） | `"Docker 容器"` |
| `scale` | string | 规模量级（并发/数据量/连接数） | `"并发约 30"` |
| `language` | string | 内容语言相关时标注语料语言 | `"中文语料"` |
| `team` | string | 团队/流程上下文（协作流程类经验） | `"5 人团队"` |

约束：
- 值统一小写技术名（`rust` 不写 `Rust`），版本号与技术名空格分隔
- 版本条目归类是确定性的（杜绝在 technologies/versions 之间摇摆）：**含数字即版本条目**（`npm 8`、`node 18`、`libssl1.1` 都算），版本号必须原样保留；`node:18` 记法规范化为 `node 18`；不含数字的纯技术名归 `technologies`
- 不确定的信息宁可不写，不造 key、不猜值
- 现有 22 条种子的 `pool`、`model` 等非标 key 属历史存量，后续新数据不再新增此类 key

## 2. source_type 使用口径

| 值 | 使用场景 |
|---|---|
| `agent` | 一切机器产出：真实 Agent 自主沉淀、LLM 蒸馏生成的四元组（含 SO/GitHub/post-mortem 导入数据） |
| `human` | 真人原创手写：本人沉淀、同事口述整理 |
| `public_import` | **本项目不使用**（导入数据统一标 `agent`，保留枚举值不迁移） |

## 3. 溯源与署名（evidence 规范）

**只有从公开网络来源导入的数据需要挂溯源 evidence，自有数据（human/agent 自主沉淀）不挂。**

每条导入数据必须挂一条 `kind='link'` 的 evidence：

```json
{
  "kind": "link",
  "label": "原帖 by {原作者用户名} · {平台}",
  "value": "https://stackoverflow.com/questions/68xxxxx"
}
```

要求：
- `value` 必须 HTTPS，指向原始出处（问题页/issue 页/文章页）
- `label` 必须含原作者署名（CC BY-SA 署名义务）
- 每条 memory 溯源 evidence 仅 1 条，计入 8 条上限
- 正文（action/outcome）只存结构化蒸馏摘要，**不搬运原文大段内容**

## 4. seeds 目录许可证声明

本目录含 Stack Overflow 衍生内容（CC BY-SA 4.0），开源发布时：

1. seeds 目录 README（即本文件）保留此声明
2. 衍生 JSON 中每条 SO 来源数据携带 evidence link（见第 3 节）
3. 不对 SO 原文做 nofollow、混淆或去除链接的处理

GitHub issue、post-mortem 博客来源：只存摘要 + 链接（合理引用），无 ShareAlike 义务。

## 5. 数据来源铁律（最高优先级，确定性、不可违背）

> 全库任何一条记忆都必须来源于**真实的、可溯源的**经验，找得到真实出处。本节为全项目最高约束，任何产出过程不得违反。

### 5.1 合法来源（只有这几类，且必须可溯源）

| 来源类别 | 内容 | 溯源要求 |
|---|---|---|
| 真实开发者问答 | Stack Overflow 等平台的真实提问 + 被采纳/高赞回答 | 必须挂原帖链接 + 作者署名（evidence） |
| 真实工程 Issue | GitHub 等仓库的真实 closed issue（含维护者修复结论） | 必须挂 issue 链接（evidence） |
| 真实复盘/Postmortem | 真实发生的线上事故复盘、根因分析报告 | 必须挂原文链接（evidence） |
| 真人原创沉淀 | 本人/同事的真实经验、口述整理 | 逐条标记 source_type=human |
| 真实论坛/社区帖子 | 掘金、HN、Reddit 等真实开发者分享 | 必须挂原帖链接 + 作者署名（evidence） |

### 5.2 绝对禁止（这些产出方式一律不可入库存量、不可新增）

- **严禁自编自造**：不允许凭空编造 `problem/action/outcome` 四元组
- **严禁"自我总结"**：不允许直接用大模型的预训练知识/常识生成"看似合理"的工程经验（这类内容裸 AI 全会，网上随手可搜，无独特性、无真实出处，一律淘汰）
- **严禁转录生成**：不得让产出模型无中生有地补充"应该怎么做""通常建议"这类泛化表述
- **严禁把知识整理冒充经验**：凡是没有真实出处、只有通用结论的条目，均判定为无效数据

### 5.3 产出过程禁令

- 蒸馏只允许做**格式变换**：把真实原帖内容转录为结构化四元组，**保留原帖语言、严禁翻译**（英文帖产出英文四元组，详见第 6 节）
- **蒸馏默认由当前对话模型在会话内直接完成（不调 API）**；`distill.py` 的 llm 模式仅作实在不行时的后备
- 蒸馏时**只浓缩原帖已经明说的内容**，不得新增模型推断、不得补全缺失结论；原帖没有明确解决结论的，直接丢弃
- 蒸馏输出必须带 `evidence`（真实出处链接 + 署名），无 evidence 的条目视为不合格
- 任何"人工生成种子脚本"（generate_*.py 之类手工成批编写条目）都是违规做法，禁止作为入库方式

### 5.4 判定口诀

> **不真实，不留；无出处，不存；自我总结，一律弃。**

人工抽检时：任何一条，问"这条哪个真实的人/哪个真实事故/哪条真实帖子讲过、在哪里"——答不上来，即不合格。

### 5.5 领域口径

种子数据领域范围：**工程问题**（编程、部署、运维、工具链、数据处理、协作流程），不含纯理论学科知识。筛选判据：裸 AI 无法可靠回答（答错/含糊/列方案无法裁决）的环境长尾与时效性问题优先入库。此口径与来源铁律同时满足（既真实可溯源，又属工程经验），缺一不可。

### 5.6 LLM 盲测（仅针对外部导入数据，public_import）

外部导入数据入库前必须过盲测，机制：

1. 把 `problem` + `conditions` 单独喂给**盲测模型**（不给真实答案），让它自己作答
2. 对比盲测答案与原帖真实解法是否**实质等价**（同一根因、同一修复方向）
3. **等价 → 丢弃**（模型本来就会，存了无增量价值）；**不等价 → 保留**（真实长尾经验）

规则：
- 判定是**二元**的（会/不会），没有分数门槛；与"质量分"（格式校验，及格线 50）是两个独立机制
- **盲测模型 = 当前对话模型（不调 API）**：由对话模型在会话中亲自作答（`blind_test.py` 工具）。理由：① 它是可用范围内最强的中文理解模型，用最强模型测，它都不会的才是真高价值（弱模型测会误放行）；② 记忆库的实际消费者就是这类 agent 模型，用它当尺子测最准
- 盲测协议必须保序（真盲）：先只看问题作答 → 全部答完 → 再对照真实解法判定。**作答阶段严禁查看 action/outcome**
- **适用范围仅限外部导入**（SO/GitHub/论坛拉取的 `public_import`）
- **agent 亲历沉淀与 human 手动沉淀不做盲测**：其价值在"亲历验证"本身（记录了实际试过什么、确实有效/无效），即使 AI 先验知道解法，实证记录仍有独特价值，盲测反而会误杀真实经历

## 6. 语言与 Embedding 模型锁定（不可变约束）

本项目**语义检索全链路只允许唯一一套模型**，禁止混用，否则向量空间不一致导致检索错乱：

- 模型：智谱 **Embedding-3**（多语言，中英统一向量空间，跨语言可检索）
- 维度：**1024**，服务端在请求体显式传 `dimensions=1024`（`server/src/main.rs` 的 EMBEDDING_DIM），与数据库 `vector(1024)` 列对齐
- 存储：**按原始语言存储，不做翻译**（不可违背）。`distill.py` 蒸馏只做结构化转换，**严禁翻译**——翻译会丢失报错原文、命令参数、术语细节等关键信息。英文帖（如 SO）产出英文四元组（`language: "en"`），中文帖产出中文四元组（`language: "zh-CN"`），逐条标 `language`
- 语言分布：随真实来源自然形成，不人为设定配比。跨语言检索由 Embedding-3 的中英统一向量空间保证

换模型（含换量化档、换维度）属于破坏性变更：需全量重向量化存量记忆，且旧向量与新增量必须在同一切换窗口内对齐。任何模型/维度调整必须先在 STANDARDS 登记并评估重向量化成本后再改代码。本地量化包（如 Ollama 不同量化档）权重配比不一致会造成相同文本向量偏移，本项目统一走云端智谱 API 规避此问题。
